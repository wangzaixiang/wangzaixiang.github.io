# Q2: Pin 的核心机制——API 设计与 Unpin

## 问题

请详细介绍 Pin 的核心 API、Unpin trait 的含义，以及它们的设计思路。

## 回答

### 一、核心概念关系

| 概念 | 含义 |
|---|---|
| **`Pin<P>`** | 一个"钉住"的包装，保证所指向的值不能移动 |
| **`Unpin` trait** | 标记此类型移动是安全的；实现了 `Unpin` 后 `Pin` 对它透明 |
| **`!Unpin`** | 标记此类型移动是不安全的；`Pin` 真正的保护对象 |

### 二、`Pin` 的核心承诺

`Pin` 承诺：**被 `Pin` 包裹的值，永远不会被安全的代码从这块内存移动走**。

```rust
use std::pin::Pin;

let value = SomeValue::new();
let pinned = Pin::new(&mut value);   // 钉住 value
// pinned 中包装的值不能再被安全移动
```

但注意：`Pin::new` 只能在 **`Unpin`** 类型上调用。

### 三、`Unpin` 是什么？

`Unpin` 是一个自动 trait。绝大多数类型都是 `Unpin` 的——`i32`、`String`、`Vec<T>`、`Box<T>` 等等。这些类型被移动后内部没有任何悬空指针，可以安全移动。

自引用类型、含有自引用的 Future 就不应该实现 `Unpin`。

### 四、`Pin` 的 API 设计

```rust
// Pin<P> 的方法签名（简化）

impl<P: Deref<Target: Unpin>> Pin<P> {
    // 只有 Unpin 类型才能安全取出可变引用
    pub fn new(pointer: P) -> Pin<P>;
    pub fn get_mut(self: Pin<&mut P>) -> &mut T;
}

impl<P: Deref> Pin<P> {
    // 任何类型都能用的方法
    pub unsafe fn new_unchecked(pointer: P) -> Pin<P>;
    pub fn as_ref(&self) -> Pin<&P::Target>;
}
```

关键设计：
- `Pin::new` 只对 `Unpin` 类型可用——安全
- 对于 `!Unpin` 类型，只能用 `unsafe new_unchecked`——程序员负责保证不移动
- `get_mut` 也只对 `Unpin` 类型可用——防止通过 `&mut T` 用 `mem::swap` 等移动值

### 五、栈上 Pin：`pin!` 宏

```rust
use std::pin::pin;

let pinned_value = pin!(SelfRef::new("hello".to_string()));
// pinned_value: Pin<&mut SelfRef>
// 这个值被钉在栈帧上，直到 pinned_value 被 drop
```

`pin!` 是 1.68 稳定的。等价于 `Box::pin` 但值在栈上。

### 六、堆上 Pin：`Box::pin`

最常用的方式：

```rust
let pinned = Box::pin(SelfRef::new("hello".to_string()));
// pinned: Pin<Box<SelfRef>>
// 值在堆上，Box 保证地址不变，Pin 保证值不移动
```

堆上更安全：`Box<T>` 分配的内存地址本身就不会变，结合 `Pin` 形成双重保证。
## 深入话题

### Unpin 的命名为什么别扭？

**直觉与实际的颠倒**：

| 直觉 | 实际 |
|---|---|
| `Pin` = "可以钉住" | 几乎所有类型都可以被 `Pin` 包裹 |
| `Unpin` = "可以拔掉钉子" | 听起来像"撤销 Pin"的操作 |

真实含义：
- **`Unpin` = "不依赖 Pin，移动也安全"** → 大多数类型
- **`!Unpin` = "依赖 Pin，移动不安全"** → 自引用类型、Future

**`Unpin` ≈ "Pin-proof"（防钉的）**——这种类型天生"免疫" Pin。被 Pin 包裹 = 没有效果，仍然可以移动；没被 Pin 包裹时也可以正常移动。

**为什么不用 `Movable`？** `Unpin` 是 auto trait，它描述的是类型"对 Pin 的抵抗力"而非"移动能力本身"。Rust 团队选择了能力式命名——表示"类型有能力在 Pin 包裹下仍然被移动"。这已经成为既定事实。

记法：**`Unpin` = "被 Pin 了之后还能 unpin 出来的"**。

### `pin!` 宏是如何定义的？

`pin!` 的核心技巧是**变量遮蔽（shadowing）**+ **借用规则**。

#### pin! 遮蔽真正防的是什么？

在安全代码中，Pin 存活时借用检查器已经阻止了通过原始变量移动：

```rust
let mut v = MyFuture::new();
let p = unsafe { Pin::new_unchecked(&mut v) };
let v2 = v;  // 编译错误！cannot move out of v because it is borrowed
```

遮蔽真正防范的是以下路径：

**1. Pin drop 后，原始变量复活：**

```rust
let mut v = MyFuture::new();
{
    let p = unsafe { Pin::new_unchecked(&mut v) };
    // poll 等操作...
} // p drop，&mut 归还

let v2 = v;  // 编译通过！但 MyFuture 内部自引用已悬空
```

**2. unsafe 裸指针绕开借用检查：**

```rust
let mut v = MyFuture::new();
let p = unsafe { Pin::new_unchecked(&mut v) };
let ptr = &raw const v;
unsafe {
    let v2 = ptr.read();  // 通过裸指针移动 v，Pin 内部引用悬空
}
```

遮蔽封死了以上路径——原始绑定不再可访问。

#### pin! 的简化实现原理

```rust
macro_rules! pin {
    ($x:expr) => {{
        // 第一步：创建可变绑定
        let mut __value = $x;
        // 第二步：Pin 包裹，同时遮蔽原绑定
        // 此后 __value 是 Pin<&mut T> 类型，原 T 不可直接访问
        let __value = unsafe { Pin::new_unchecked(&mut __value) };
        __value
    }};
}
```

关键安全保障：
1. **遮蔽**：第二个 `let __value` 遮蔽了第一个，原始 `T` 不再能通过名称访问
2. **借用规则**：`Pin<&mut T>` 持有了对原始 `T` 的独占引用，Rust 的借用检查保证 `T` 不能被移动或别名访问
3. **Drop 安全**：当 `Pin` 被 drop 时，引用释放，编译器自动插入对原始 `T` 的 `drop` 调用

#### 栈帧布局

```
[  T 的值  ]  <-- 实际的 T，固定在栈帧的偏移处
     ↑
[ &mut T  ]  <-- Pin<&mut T> 内部的指针
     ↑
__value (Pin<&mut T>)  <-- 对外暴露的句柄
```

移动 `__value`（`Pin<&mut T>`）只是复制了栈上的引用/指针，底层的 `T` **不会移动**。`T` 牢牢钉在栈帧的固定偏移处，直到整个块结束。

#### 标准库的真实实现

标准库（`std::pin::pin`）实际更简洁，利用了块表达式 + 临时位置延长：

```rust
// 标准库真实签名（简化）
macro_rules! pin {
    ($x:expr $(,)?) => {
        // { $x } 创建临时位置，&mut 取引用，Pin 包裹
        // 临时位置存活到 Pin<&mut T> 被 drop
        $crate::pin::Pin::new_unchecked(&mut { $x })
    };
}
```

- `{ $x }`：块表达式，值被求值并放在一个临时的匿名位置
- `&mut { $x }`：取该临时位置的独占引用（临时位置生命周期延长到语句结束）
- `Pin::new_unchecked`：包装引用 → 返回值持有引用，临时位置跟随返回值存活

### 为什么 `!Copy` 不够——`Pin` 真正要堵的漏洞

`!Unpin` 的类型必然是 `!Copy` 的，但 `!Copy` 只能阻止通过 `&T` 的移动——无法阻止通过 `&mut T` 的 swap/replace：

```rust
let mut a = SelfRef::new("hello".to_string());
let mut b = SelfRef::new("world".to_string());

// 安全代码，编译器完全允许：
std::mem::swap(&mut a, &mut b);
// a 和 b 的字节完全交换
// a.ptr 和 b.ptr 互相指向对方原来的栈地址 → 悬空
```

**`&mut` 给了调用方 swap / replace / take 的权力——不需要 Copy，不需要所有权，只靠独占引用就可以重排内存。**

```
                     &T          &mut
!Copy 是否阻止？     ✅ 阻止        ❌ 不阻止（swap 不需要 Copy）
Pin 是否阻止？       N/A 不需要    ✅ 封死 <—— Pin 存在的理由
```

**Pin 的本质是剥夺 `&mut` 造成的"原地交换/替换"的能力。** 整个 Pin 体系的运行时价值浓缩于一处：对 `!Unpin` 类型的 `Pin<&mut T>`，不给 `get_mut`。

### `Pin<&T>` 的必要性——类型记账而非运行时安全

`Pin<&T>` 在运行时安全层面不提供比裸 `&T` 更多的保护——`&T` 已经阻止了 swap/replace。它的价值是类型系统的 plumbing：

1. **API 一致性**：`Pin::as_ref()` 返回 `Pin<&T>`，保持 Pin 链不断。如果直接返回 `&T`，下游想再用 Pin 就得 unsafe 重构。

2. **泛型兼容**：`fn f<T>(val: Pin<impl Deref<Target = T>>)` 统一接受 `Pin<&T>`、`Pin<&mut T>`、`Pin<Box<T>>`。

3. **契约标记**：`Pin<&dyn Future>` 在类型层面告知调用方"这个值是被钉住的"，虽然运行时和 `&dyn Future` 行为相同。

| | `&T` | `Pin<&T>` |
|---|---|---|
| 阻止移动 | ✅ 已经阻止 | ✅ 同样 |
| 阻止 swap/replace | ✅ 没有 `&mut` | ✅ 同样 |
| 额外安全收益 | — | **没有** |

真正干活的是 `Pin<&mut T>` + `!Unpin` → 封死 `get_mut`。其余都是类型层面 plumbing。
