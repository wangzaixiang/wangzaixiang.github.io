# Q1: 为什么需要 Pin？——自引用类型的移动问题

## 问题

请介绍 Rust 中的 Pin 特性为什么被设计出来，它要解决什么问题？

## 回答

### 一、核心问题：自引用类型被移动后指针悬空

`Pin` 的存在是为了解决**自引用类型（self-referential types）在内存中被移动后，内部指针失效**的问题。

看下面这个自引用结构体：

```rust
struct SelfRef {
    data: String,
    // 指向 self.data 的引用
    ptr: *const String,  // 裸指针，绕开借用检查
}

impl SelfRef {
    fn new(s: String) -> SelfRef {
        let mut sr = SelfRef { data: s, ptr: std::ptr::null() };
        sr.ptr = &sr.data as *const String;
        sr
    }

    fn print(&self) {
        println!("ptr points to: {}", unsafe { &*self.ptr });
        println!("data field:    {}", self.data);
    }
}
```

创建后直接使用，正常工作：

```rust
let sr = SelfRef::new("hello".to_string());
sr.print();
// ptr points to: hello
// data field:    hello
```

### 二、移动带来的问题

当 `sr` 被移动后（赋值给另一个变量、传递给函数、从函数返回等），`self.ptr` 仍然指向旧的内存地址：

```rust
let sr = SelfRef::new("hello".to_string());
let sr2 = sr;   // 移动！栈上字节被拷贝，原地址失效
sr2.print();    // 危险！ptr 仍指向旧地址
```

在 Debug 模式下旧地址可能还没被覆盖，"碰巧"正确；在 Release 模式下编译器可能重用那块内存，结果不可预测。

### 三、为什么 Rust 的借用检查器没拦住？

因为裸指针（`*const T`）绕过了借用检查器。安全 Rust 中本来就不会出现自引用——借用检查器会把 `&self.data` 的引用和 `self` 的完整所有权绑定在一起，使得你无法同时拥有引用和可变访问。但 `unsafe` 代码中的裸指针不受此限制。

### 四、什么场景会产生自引用？

现实中最大的场景就是 **`async` 生成的 Future**：

```rust
async fn example() {
    let local = String::from("hello");
    let future1 = do_something(&local).await;
    // future1 内部可能引用了 local
}
```

编译器生成的匿名 Future 结构体包含了 `local` 和对 `local` 的引用——这本质上就是一个自引用结构体。这就是为什么 `Future` 通常不是 `Unpin` 的。
