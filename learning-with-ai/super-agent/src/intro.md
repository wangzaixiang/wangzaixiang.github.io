# Super-agent：从会话到常驻系统

2026 年 10 月 31 日，DeepSeek Harness 团队发布了
《Super-agent 设计探索：迈向更自主的 Agent 系统》，并开源了研究原型
`dsh-superagent-prototype`。这篇文章没有提出新的模型，而是把一个系统问题摆到了台面上：

> 当模型执行单个任务越来越少需要人干预时，限制生产力进一步提升的瓶颈，
> 正在从“模型能力”转向“人的注意力”。

Super-agent 是对一种 Agent 形态及其系统架构的命名：

> **一个跨会话保持上下文、并行推进多项任务且互不干扰、持续在线、能主动响应环境事件的连续实体。**

它具备四个基础特征：

| 特征 | 含义 | 用户感受 |
|---|---|---|
| 连续 | 跨 IM、GitHub、邮件等信道保持同一份上下文 | 始终只有一个 Agent，不用想“X 信息在哪个 Session 里” |
| 高效 | 并行推进多个复杂任务，随时接受新指令 | 不用等上一个任务结束 |
| 主动 | 观察环境事件，按规则主动推进 | 没人 @ 也能发现并处理值得做的事 |
| 持久 | 始终在线，接入真实工作环境，异常后自动恢复 | 设备休眠、进程崩溃不会让任务消失 |

## 这本书要解决的问题

围绕 Super-agent，常见的问题有五类：

1. **概念**：它和“多开几个聊天窗口”“多 Agent 协作”“Agent Team”到底有什么区别？
2. **架构**：Router/Worker 双层、事件驱动、存算分离、Watchdog 分别解决什么问题？
3. **机制**：订阅直通、两级过滤、Inline & Spill、链式召回、异步 ReAct 是怎么工作的？
4. **实现**：原型的领域模型、授权、状态机、恢复语义如何落地？
5. **判断**：实验数字能信多少？什么时候不该用？安全边界在哪里？

本书按“问题 → 架构 → 设计 → 实现 → 验证 → 边界”的顺序展开。每章尽量只回答一个问题，
并把关键机制还原成可计算的模型，而不是停留在术语层面。

## 一个重要的前提

Super-agent 目前是**面向工程实践的架构探索**，不是成熟产品。官方原型的 README 明确写着：

> Research prototype for reference only, not an official DeepSeek product.

因此本书区分三类陈述：

- **原文主张**：DeepSeek 团队在文章中明确写出的设计意图与实验结论。
- **实现事实**：官方原型仓库的文档、源码和测试能直接验证的行为。
- **分析推断**：本书基于前两类事实做出的对比、批判与落地建议，会明确标注。

这三类陈述的可信度不同，阅读时需要分清。

## 先记住一句话

> **Super-agent 的本质不是“更聪明的 Agent”，而是“把会话管理从用户手里拿走，交给系统”。**

它的收益是人的注意力被释放；它的代价是更多 token、更复杂的调度、更难的故障恢复与安全边界。
后面所有设计，都是在为这个交换定价。
