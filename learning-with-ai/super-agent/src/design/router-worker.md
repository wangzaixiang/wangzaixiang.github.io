# 双层调度：Router 与 Worker

## 3.1 根本权衡：连续性与吞吐量

跨信道连续交互与多任务高效并发之间存在一个根本权衡：

| 方案 | 连续性 | 吞吐量 | 主要问题 |
|---|---|---|---|
| 全部交给一个 Session | 最高 | 最低 | 单 ReAct Loop 串行；细节混杂；被新消息打断 |
| 每条事件新开 Session | 最低 | 最高 | 缺全局上下文；结果割裂；多 Session 各自回复 |
| 双层：Router + Worker | 高 | 高 | 多一个全局节点；需要分派、订阅、恢复机制 |

Super-agent 的选择不是“消灭权衡”，而是**把权衡放到不同的层**：

- Router 层承担连续性：它是全局序点（Sequence Point）、协调点和记忆。
- Worker 层承担吞吐量：每个 Worker 在独立上下文中专注单一任务。

用户侧只感知一个 Agent；系统内部才有多会话。

## 3.2 Router 层：只分派，不干活

### 职责

1. 承接所有入口的人类交互（IM、GitHub、邮件、面板）。
2. 维护跨任务的全局上下文与记忆。
3. 判断新事件是否开启新工作，并分派给 Worker。
4. 汇总 Worker 的状态与结果，统一对外回复。
5. 处理跨任务协调与少量冲突。

### 非职责

- 不执行具体任务；
- 不做单任务内部的步骤拆解；
- 不直接操作代码仓库；
- 甚至可以不配备 Bash 工具。

这不是“能力不足”，而是**架构约束**：Router 是全局节点，一旦它开始干重活，
就会成为吞吐瓶颈和故障单点。

### 为什么可以用较轻量的模型

Router 的每一步通常是：

- **长输入**：一批事件、Thread 快照、Ticket 列表、策略；
- **短输出**：一个 accept/stop/ignore 决定，或一条分派指令。

它不需要深度技术推理，只需要理解任务之间的高层关联、判断授权与范围。
因此原文指出：Router 层任务常常没有想象中复杂，较轻量的模型往往就能兼顾速度与效果。

### 一个反直觉的结论：单 Router Session 没那么容易成为瓶颈

原因是**批处理（Batching）**：

- 事件流平稳时，Trigger 逐条进入 Router，单次响应延迟低；
- 事件密集时，上一轮推理期间到达的 Trigger 会积压，在下一轮 LLM 调用中一并注入。

Router 只做轻量交互与分派，每步是“长输入、短输出”。把多条 Trigger 合并进一次 LLM API 调用，
会在 Prefill 阶段并行计算，因此单次请求耗时的增长远慢于批处理大小。

原文压测数据：

| 指标 | 低到达率（约 1 条/分钟） | 高到达率（约 40 条/分钟） |
|---|---:|---:|
| 平均 batch 大小 | 1.0 | 2.8 |
| 单次请求耗时 | 2.5 s | 3.9 s |
| 单个决定分摊的推理时间 | 6.4 s | 1.6 s |

### 批处理的量化模型

设 batch 大小为 $b$，单次请求耗时为 $T(b)$。分摊到每个决定的时间为：

$$
A(b) = \frac{T(b)}{b}
$$

如果 $T(b)$ 随 $b$ 亚线性增长（Prefill 并行），则 $A(b)$ 随 $b$ 下降。
用表中数据粗算：

$$
A(1) = 2.5/1 = 2.5\text{ s}
$$

$$
A(2.8) \approx 3.9/2.8 \approx 1.39\text{ s}
$$

与原文报告的 $6.4 \rightarrow 1.6$ s 同量级，但数值并不完全一致。
原文没有给出 6.4 s 的完整分解；它更像是包含排队、调度与端到端等待的“每个决定实际分摊时间”，
而不是纯推理耗时。**不要把 6.4 → 1.6 当作纯推理加速比**，它衡量的是系统在高负载下的有效吞吐改善。

批处理的上限由两个因素决定：

1. **上下文长度**：一批 Trigger 加上 Thread 快照、Ticket 列表、策略，不能超过模型窗口；
2. **单轮准确处理能力**：模型在一轮里能准确区分多少条 Trigger，而不混淆。

超过上限后，批处理收益递减，甚至因注意力稀释而判断质量下降。

### 什么时候需要切分 Router

单个 Router Session 在团队规模下够用，不代表永远够用。规模扩大后有两条路：

- **多层过滤**：Router 内部再分快慢层，先由轻量规则/小模型筛，再交给主 Router；
- **水平切分（Sharding）**：按任务类型、团队、项目拆成多个 Router Session。

切分粒度越细，并发吞吐越高，但分片之间的记忆与上下文连续性越低。
在全局记忆问题解决之前，这个权衡始终存在。

## 3.3 Worker 层：只干活，不抢话

### 职责

1. 在独立上下文中完成一个具体任务；
2. 挂载完整执行工具（Bash、文件、GitHub、浏览器等）；
3. 向 Router 汇报状态与结果；
4. 处理自己订阅的 Thread 上的后续事件；
5. 在范围内自行解决冲突，范围外交回 Router。

### 非职责

- 不直接与人类交互；
- 不把推理过程和工具调用直接输出到外部信道；
- 不自行扩大授权范围。

### 为什么 Worker 要用最强模型

Worker 直接决定任务结果与代码质量。Router 的判断错了，最多是分派错；Worker 的执行错了，
就是交付物错了。因此原文明确：Worker 通常配置能力最强的模型。

### Worker 之间如何解决冲突

多任务并发时，Worker 之间通常不需要直接通信。冲突往往出现在共享工作环境，例如同一个
Pull Request。解决办法不是点对点消息，而是**订阅同一个 Thread**：

- 多个 Worker 订阅同一个 PR/话题；
- 该 Thread 下的新事件同时直通给所有订阅者；
- 每个 Worker 都能看到别人的操作，有机会自行发现并解决冲突；
- 少数跨任务协同由 Router 中转。

这相当于用“共享事件流”替代“显式消息总线”，降低了 Worker 之间的耦合。

### Worker 内部可以再嵌套

Worker 不必是单个 Session：

- 执行复杂单任务时，可以再创建 Subagent；
- 也可以本身就是一个 Agent Team。

这些内部结构对 Router 透明。Router 只关心“这个 Ticket 的进展”，不关心 Worker 内部用了几层。

## 3.4 Router/Worker 与 Agent Team 的区别

这是最容易混淆的一点。两者表面都是“一个中心节点分派多个执行节点”，但侧重点不同。

| 维度 | 常见 Agent Team | Super-agent 双层 |
|---|---|---|
| 拆分对象 | **单个复杂任务内部**的步骤/角色 | **多个任务之间**的关联与分派 |
| Team Lead 的负载 | 深入理解任务细节、规划子任务、高频协调 | 只做高层分派、对外交互、全局记忆 |
| 子任务耦合度 | 通常较紧 | 通常较松，独立推进 |
| 上下文 | 共享或频繁同步 | Worker 彼此隔离 |
| 失败影响 | Lead 被细节拖垮，整个任务受影响 | 单个 Worker 失败，其他任务继续 |
| 能否用轻量模型 | 通常不能，Lead 需要强推理 | 可以，Router 只需判断与分派 |

原文甚至指出：如果通过提示词约束一个 Agent Team 的主会话不亲自执行具体任务，
仅负责对外交互并把不同任务分派给各成员独立推进，那么它也可以视为这种双层架构。
**关键不在名字，而在职责边界是否真的分开。**

## 3.5 并发控制：Worker Slots 与人的优先级

原型实现给了一个很工程化的细节：

- 每个 Ticket 在启动或唤醒时占用一个 Worker Slot；
- 配置的并发上限约束这些 Slot；
- **人的消息或状态查询可以额外占用一个 Slot**，即使正常 Slot 已满；
- 人的唤醒优先于新任务启动。

这保证了一个重要性质：

> 新工作不能阻止一个人继续推进已有的 Ticket。

如果没有这个优先级，系统在满负载时会出现“人想介入却排不上队”的反直觉行为，
把“自主”变成“失控”。

## 3.6 失败模式与缓解

| 失败模式 | 表现 | 缓解 |
|---|---|---|
| Router 成为瓶颈 | 事件排队、响应变慢 | 批处理、订阅直通、轻量模型、必要时分片 |
| Router 上下文稀释 | 分派判断变差、忘记旧任务 | Inline & Spill、链式召回、限制单轮 Trigger 数 |
| Worker 冲突 | 同一 PR 上重复修改/互相覆盖 | 多对多订阅、共享 Thread 事件、Router 中转 |
| Worker 失控 | 无效循环、偏离目标 | Watchdog、最大步数/超时、人工停止 |
| 回复混乱 | 多个 Session 各自说话 | Worker 不直接对外，Router 统一回复 |
| 资源饥饿 | 新任务占满 Slot，人无法介入 | 人类消息额外 Slot、唤醒优先 |

## 3.7 小结与思考题

**小结**：双层架构的核心不是“多一个 Router”，而是**把连续性和吞吐量分别交给最适合的层**。
Router 通过“只分派 + 批处理 + 轻量模型”避免成为瓶颈；Worker 通过“隔离上下文 + 完整工具 + 订阅共享环境”
实现高质量并发。两者之间的边界，就是 Super-agent 与 Agent Team 的分水岭。

**思考题**：

1. 为什么 Router “不配 Bash”是一个架构决策，而不只是权限设置？
2. 批处理为什么对“长输入、短输出”特别有效？对“长输出”任务是否同样有效？
3. 如果 Worker 之间必须频繁通信，订阅模式还够用吗？什么情况下需要引入直接通信？
4. 设计一个 Router 分片方案，说明你按什么维度切、会损失什么连续性。
5. 人类消息额外 Slot 的规则，会不会导致新任务饥饿？如何平衡？
