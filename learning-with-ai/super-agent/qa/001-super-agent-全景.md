# 001：Super-agent 全景 —— 概念、架构与第一性判断

> 第 1 期学习记录 | 对应正文第 1-10 章 | 目标：建立一张能自己讲清楚的心智地图

## 资料来源与可信度

本期以 DeepSeek Harness 2026-10-31 原文为主干，官方原型仓库为工程事实来源，
Anthropic 三篇工程文章为对照。用户提供的知乎链接在当前环境返回 HTTP 403，
未作为独立信源；详见[参考资料](../src/appendix/references.md)。

---

## Q1：一句话说清 Super-agent 是什么？

**A**：它是一种 Agent 形态与系统架构：**跨会话保持上下文、并行推进多项任务且互不干扰、
持续在线、能主动响应环境事件的连续实体**。

关键不在“更聪明”，而在“把会话管理从用户手里拿走，交给系统”。用户面对的是一个 Agent，
系统内部才有多会话。

四个特征：

| 特征 | 一句话 |
|---|---|
| 连续 | 跨 IM/GitHub/邮件保持同一份上下文 |
| 高效 | 多任务并行，随时接受新指令 |
| 主动 | 观察环境事件，按规则推进 |
| 持久 | 始终在线，异常后自动恢复 |

---

## Q2：为什么“多开几个 Session”不够？

**A**：因为 Session 同时承担了两件事：

1. 技术上的上下文管理；
2. 面向用户的项目管理。

当两者绑在一起，用户必须手动切换、自己记住每个 Session 的上下文。原文观察到的经验上限是
一个人只能同时跟进 **3 到 5 个活跃 Session**。模型越强，单任务越自动，人越想多开任务，
这个上限就越成为瓶颈。

“多开 Session”只是把瓶颈从模型转移到了人的注意力，没有消除它。

---

## Q3：四个特征分别由哪个模块支撑？

**A**：不是一一对应。

| 模块 | 支撑特征 | 核心机制 |
|---|---|---|
| 双层架构 | 连续 + 高效 | Router/Worker、批处理、订阅直通 |
| 事件驱动 | 主动 | Trigger/Thread、两级过滤、投机执行 |
| 面向人的交互 | 连续 + 高效 | 异步 ReAct、全双工、多信道 |
| 计算/状态/环境分离 | 持久 | 无状态计算、持久日志、端侧 daemon、BYOM |
| 外部 Watchdog | 持久 | 外部控制回路、基础设施 + 任务进展监控 |

这说明 Super-agent 不是“功能拼盘”，而是多组机制协同解决四组约束。

---

## Q4：Router 只做分派，为什么反而更快？

**A**：三个原因。

1. **职责窄**：Router 只处理“任务之间”的高层关联，不做单任务内部拆解，每步是长输入、短输出。
2. **可批处理**：上一轮推理期间积压的 Trigger，会在下一轮 LLM 调用中一起注入。Prefill 阶段
   并行计算，单次请求耗时的增长远慢于 batch 大小。
3. **可用轻量模型**：Router 不需要深度技术推理，较轻量的模型就能兼顾速度与效果。

原文压测：到达率从约 1 条/分钟升到约 40 条/分钟，平均 batch 从 1.0 升到 2.8，
单次请求耗时只从 2.5 s 升到 3.9 s，单个决定分摊时间从 6.4 s 降到 1.6 s。

**注意**：6.4 → 1.6 不是纯推理加速比，它包含排队/调度等端到端分摊；原文没有给出完整分解。

---

## Q5：订阅直通解决什么问题？

**A**：避免 Router 转发所有后续事件。

- 新任务：Router 判断并创建 Worker（Slow Path）。
- 已订阅的后续事件：程序直接发往 Worker（Fast Path），不经过 Router。
- Router 仍可观测所有事件以掌握全局状态，但只判断尚未被订阅的新事件。

效果：完成时间基本不变，但 Router 决定数减少约 30%。以直通版本 23.23M 读缓存 token 为基线，
去掉直通后增至 31.77M（+37%）。直通的价值是省资源、留余量，不是让任务更快。

多对多订阅还有一个副作用：同一个 PR/Thread 的新事件会同时发给所有订阅者，Worker 不需要
点对点通信，就能看到彼此的操作并自行解决冲突。

---

## Q6：事件过滤为什么是“程序 + 模型”两级？

**A**：因为真实事件流是“高噪音、低触发率”，全部交给模型太贵、太慢。

- 程序层（Fast Path）：来源、群组、白名单等确定性条件，先挡掉大部分噪音。
- 语义层（Slow Path）：只把候选交给 LLM，判断是否需要行动。

成本模型：

$$
C_{\text{two-level}} = N c_f + N p c_s
$$

只要程序层通过率 $p < 1 - c_f/c_s$，就比全部交给模型便宜。

过滤质量要看精确率与召回率，而不是越严越好。主动场景里，误判（FP）的代价通常高于漏判（FN），
所以默认应偏向高精确率、低打扰。原型的 `observe` 模式就是先记录“本来会做什么”，再切 `auto`。

---

## Q7：Inline & Spill 与链式召回是什么关系？

**A**：Inline & Spill 是**上下文组织策略**，链式召回是**多跳检索机制**。

- Inline：近期很可能用到的信息直接放进窗口，省一次工具调用。
- Spill：超预算/低频内容留在窗口外，只留引用/摘要，按需读取。
- 链式召回：给 Trigger/Thread/Worker Session 等对象唯一 ID；每次注入内联下一跳 ID；
  模型沿引用图逐跳展开上下文。

一句话：**把上下文窗口当 Cache，把对象关系当指针图。**

它不等同于 RAG：RAG 靠相似度，链式召回靠显式引用关系；也不等同于摘要压缩：Spill 保留可回溯的
原始内容。链式召回的失败模式是断链、摘要失真、跳数过多导致成本上升。

## Q8：异步 ReAct 如何做到全双工？

**A**：把同步 `run()` 改成异步 `start()` / `stop()`：

- `start()` 立即返回“已启动”，循环不再等待；
- 后台完成后，结果作为一条新事件消息投递进会话；
- `stop()` 可以主动终止执行过长的后台命令；
- 新输入在当前推理步结束后处理，不必等后台工具完成。

原文说明这项机制已在 DeepSeek Harness 中实现，但**尚未默认开启**。异步带来新的状态问题：
结果顺序、重复/丢失、取消边界、上下文膨胀、人的介入时机。

---

## Q9：存算分离与 Watchdog 为什么必须一起看？

**A**：存算分离解决“计算可以重启”，Watchdog 解决“系统能自己发现异常并恢复”。

两步解耦：

1. 计算与状态分离：云端无状态 Harness + 持久化会话日志；容器可重启、可替换。
2. 计算与环境分离：执行环境留在原地，端侧只放轻量 daemon；支持 BYOM、跨设备、间歇在线。

Watchdog 是主系统之外的独立 Agent Session，用定时消息驱动：

- 监控基础设施（接口报错、状态恢复失败）；
- 监控任务进展（Worker 是否有实质进展、方向是否偏离）；
- 能在线修复（改提示词、调规则）；
- 本身也需要被监控。

恢复语义的核心是“至少一次 + 幂等”，而不是昂贵的“恰好一次”。

## Q10：原型的授权模型如何防止“主动”变成“越权”？

**A**：四个关键设计。

1. **显式 vs 推断**：白名单内的人明确请求才是 explicit；bot 永远不能产生 explicit。
2. **三种 accept mode**：`off` / `observe`（默认，只记录“would accept”）/ `auto`。
3. **Mandate 不可变**：记录范围、强度、Policy 版本、匹配规则；只有人的 stop 能撤回，
   Policy 不再成立时撤销；恢复前重新验证。
4. **上下文与授权分离**：订阅 Thread 只让 Worker 看到事件，不授予新权限；看到不等于可以做。

原型的包装器/目录只是默认值，不是安全边界；Worker 仍可能通过绝对路径执行程序。
安全仍是原文列出的开放问题。

---

## Q11：实验数字能信到什么程度？

**A**：分组看。

| 结论 | 可信度 |
|---|---|
| 双层架构完成时间更短、尾部更稳 | 中：5 次运行、合成负载，但对比清晰 |
| 订阅直通省 Router token/决策 | 中：同负载消融，方向明确 |
| Router 批处理提升突发吞吐 | 中：真实模型 + Mock Worker，范围有限 |
| 单 Session 委派行为对提示词高度敏感 | 强：0/5 vs 4/5 委派率 |
| 任务质量更高 | **未证明**：编码工作被替换为 sleep 工具 |
| 真实生产更优 | **未证明**：合成负载、简化环境、时间缩放 |
| 更便宜 | **未证明**：只报告读缓存 token，没有总成本 |
| 长期稳定/安全 | **未证明**：实验时长与对抗测试不足 |

实验衡量的是**调度与协作能力**，不是任务执行质量。12.4 分钟是缩放后的实验时间，不是产品 SLA。

## Q12：什么时候不该用 Super-agent？

**A**：

- 一天只有几个任务：双层与持久化复杂度不划算；
- 任务高度耦合、必须共享同一份上下文：Worker 隔离会破坏连续性；
- 需要严格确定性/可复现：模型决策本质不确定；
- 安全边界无法定义：主动 + 多设备会放大风险；
- 结果无法验证：自主执行容易产生难以发现的质量问题；
- 没有 observability：出问题无法定位，恢复无从谈起；
- 单仓库/单任务的小工具：单 Session + 工具足够。

## 本期结论

1. Super-agent 的第一性问题是**人的注意力**，不是模型能力。
2. 它的核心手法是**把 Session 降级为系统实现**，用双层架构分离连续性与吞吐。
3. 事件驱动、Inline & Spill、链式召回、投机执行，都是经典系统思想在 Agent 上的迁移。
4. 持久在线的关键是**计算/状态/环境三者解耦** + 外部 Watchdog。
5. 它的代价是更多 token、更复杂的调度、更难的恢复与安全；适用边界比“能力”更重要。
